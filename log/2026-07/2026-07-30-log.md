## OpenFOAM research lead

### Bottom line

The RCCM author's suggestion to “try OpenFOAM” is technically relevant, but it
is not a complete instruction. OpenFOAM is a mature C++ computational
continuum-mechanics platform, best known for computational fluid dynamics. It
provides meshes, dimensioned scalar/vector/tensor fields, finite-volume
operators, linear solvers, boundary conditions, parallel execution, and
post-processing. It does **not** decide which physical fields, constitutive
laws, initial conditions, or observables constitute RCCM.

The strongest current interpretation is:

> Use OpenFOAM as a second numerical laboratory and a foreign implementation
> against which to cross-examine TauLab, then add RCCM-specific equations only
> when their closure and provenance are explicit.

This could produce valuable numerical evidence. It cannot by itself validate
RCCM, convert a fluid analogy into a physical identity, or repair a missing
equation.

### The terrain

An OpenFOAM simulation, called a **case**, is roughly this pipeline:

```text
governing PDEs + constitutive model + parameters
        + geometry/mesh + initial/boundary conditions
        + discretisation/solver controls
    → evolved fields
    → conservation, convergence, and observable measurements
```

The usual case directories make those boundaries visible:

- `0/` holds initial fields and their boundary conditions;
- `constant/` holds the mesh, material properties, and physical models; and
- `system/` holds time control, finite-volume schemes, and equation-solver
  controls.

This is a strong match for the repository's theory-compiler discipline.
OpenFOAM also attaches dimensions to field data and checks operations for
dimensional compatibility. Its C++ equation syntax can closely mirror a PDE;
for example, time derivative, divergence, Laplacian, and pressure-gradient
operators are expressed as field operations rather than hand-written loops.
These capabilities are described in the OpenFOAM Foundation's
[v14 introduction](https://doc.cfd.direct/openfoam/user-guide-v14/introduction),
[programming-language guide](https://doc.cfd.direct/openfoam/user-guide-v14/programming-language-openfoam),
[case-file map](https://doc.cfd.direct/openfoam/user-guide-v14/case-file-structure),
and
[dimensioned-file format](https://doc.cfd.direct/openfoam/user-guide-v14/basic-file-format).

### Where RCCM fits—and where it does not

The current formal source explicitly proposes an “Admittance-Modified
Navier-Stokes Equation” and later identifies pressure, velocity-gradient,
stress, strain, and acoustic-wave objects with spacetime and force objects.
That makes OpenFOAM an appropriate place to test the **continuum equations**.
It does not make the asserted physical identifications true.

| RCCM/TauLab object | Natural OpenFOAM representation | Present status |
|---|---|---|
| Density `ρ` | cell-centred scalar field | Native |
| Velocity `v` / momentum | vector field plus mass flux | Native |
| Pressure and total energy | thermophysical scalar fields | Native for standard compressible models |
| Continuity and momentum balance | finite-volume conservation equations | Native machinery |
| Compressible acoustic propagation and shocks | `fluid` or density-based `shockFluid` module | Native reference-physics baseline |
| Maxwell-type elastic memory/stress | symmetric tensor stress plus relaxation model | Native model family in Foundation v14 |
| Giesekus/PTT alternatives | viscoelastic rheology models | Native model family in Foundation v14 |
| RCCM admittance tensor `α` and its sector-specific force throttling | tensor field and custom stress/source operators | RCCM-specific; must be implemented and audited |
| Independent microrotation / intrinsic angular momentum | vector field plus angular-momentum and couple-stress equations | Custom; not supplied by an ordinary fluid solver |
| Diffuse cavity/order parameter and chemical potential | scalar phase field plus custom evolution/free-energy law | Custom; standard VOF/cavitation is not automatically the RCCM object |
| “Gravity,” “charge,” “spin,” or particles emerging from the fields | post-processed candidate observables with discriminating tests | Not supplied by OpenFOAM and not established by a visual resemblance |

Foundation v14 now includes Maxwell, Giesekus, and Phan-Thien–Tanner
viscoelastic models, including multiple relaxation modes. That makes it more
useful for TauLab than a generic CFD package would be; see the
[v14 transport/rheology guide](https://doc.cfd.direct/openfoam/user-guide-v14/transport-rheology)
and
[v14 release notes](https://openfoam.org/release/14/).
It still does not combine RCCM's compressible, viscoelastic, micropolar,
diffuse-interface, and admittance-modified pieces into one ready-made solver.

Two external projects are useful as implementation references, not as RCCM
solvers:

- [rheoTool](https://github.com/fppimenta/rheoTool) adds extensive
  viscoelastic and electrically driven flow machinery, but its published
  branches target OpenFOAM 9/7 and foam-extend 4; and
- [epotMicropolarFoam](https://github.com/KEAslani/epotMicropolarFoam) shows
  that an independent microrotation field can be added to OpenFOAM, but it is
  an incompressible MHD blood/ferrofluid solver based on OpenFOAM 6—not RCCM.

Their existence supports feasibility of custom field equations. Their results
do not transfer scientific support to RCCM.

### What “try it” should mean first

The smallest honest experiment is **not** a cinematic vortex or a custom
gravity simulation. It is an independent reproduction of the already measured
TauLab acoustic baseline using a standard OpenFOAM solver.

Lock the same problem before looking at OpenFOAM's output:

```text
equations: inviscid compressible ideal-gas Euler
domain:    periodic unit interval, represented by a one-cell-thick 3D mesh
gamma:     1.4
rho0:      1
p0:        1
delta(x):  1e-4 sin(2πx)
rho(x):    1 + delta
u(x):      sqrt(1.4) delta
p(x):      1 + 1.4 delta
end time:  0.25 / sqrt(1.4)
grids:     32, 64, 128 cells
```

The likely starting module is Foundation v14
[`shockFluid`](https://doc.cfd.direct/openfoam/user-guide-v14/solvers-modules):
it is a density-based finite-volume solver for compressible flow with an
inviscid path. Before executing it, the exact thermophysical model, flux
scheme, cyclic patches, and field-to-TauLab normalization must be recorded.
The acceptance card should require:

1. measured wave speed within the same predeclared one-percent gate;
2. decreasing density-field error across `32/64/128`;
3. reported mass, momentum, and energy ledgers;
4. no parameter tuning against TauLab's final field; and
5. a comparison that preserves differences in discretisation rather than
   forcing bitwise agreement.

A pass would mean two different code paths reproduce the same standard
continuum benchmark. It would strengthen confidence in TauLab's numerical
hydrodynamic foundation, not in RCCM's novel physical claims.

The second useful experiment would be a standard viscoelastic benchmark that
compares OpenFOAM's Maxwell stress relaxation with TauLab's local relaxation
and, later, its stress feedback. Only after those two reference-physics marks
should an `rccmFoam`-like custom module be considered. That module would need
the complete declared state, free energy/equation of state, constitutive laws,
source terms, boundary data, and observables from one immutable theory bundle.

### Version and machine boundary

“OpenFOAM” currently names two actively maintained but divergent
distributions. As of 2026-07-30, the OpenFOAM Foundation line is
[v14](https://openfoam.org/version/14/), while the OpenCFD/Keysight line is
[v2606](https://www.openfoam.com/current-release). A reproducible experiment
must name the distribution, exact release/patch, and container or VM image; an
unqualified “OpenFOAM” version is insufficient.

For this Apple-silicon Mac, Foundation v14's supported route is ARM64 Ubuntu in
[Canonical Multipass](https://openfoam.org/download/14-macos/).
Local reconnaissance found no `foamRun` or `multipass` executable. A Docker
client is present, but no OpenFOAM image was pulled and no OpenFOAM simulation
was run during this research pass. The Foundation v14/patch `20260724` route
is the current leading candidate for a pinned reference environment.

This VM/container path is CPU-oriented and does not replace TauLab's native
Metal work. OpenFOAM's value here is mature continuum infrastructure,
unstructured meshes, model libraries, MPI scaling, and a genuinely separate
implementation path. TauLab should retain theory hashing, provenance and
intervention ledgers, deterministic replay, the double-precision oracle, and
Metal parity.
